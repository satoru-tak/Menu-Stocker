## 0. 用語の定義

このプロジェクトで言葉のブレを防ぐため、最初に用語を決めておく。

| 用語 | 意味 |
| --- | --- |
| **レシピ** | 1つの料理を表す「箱」。料理名・写真・元の情報（動画URLなど）を持ち、中に1つ以上の**版**を持つ |
| **版**（バージョン） | レシピの中身（材料・分量・手順）の1つの形。最初に登録したものが**元の版**、自分で手を加えたものが**アレンジ版**（版1、版2…）。分量の調整や調味料の変更など、**同じ料理の範囲での変化**は版として残す |
| **元の版** | レシピを最初に登録したときの版。削除できない（アレンジ版は自由に削除・保存できる） |
| **派生レシピ** | 既存のレシピをもとに作った**別の料理**。主な食材が変わる（例：鶏の照り焼き → 豚の照り焼き）など、同じ料理とは言えない変化のときに使う。独立したレシピとして扱い、**どのレシピから派生したか**のつながりを持つ |
| **献立** | 「いつ何を作るか」の**予定**（例：月曜の夜は肉じゃが）。カレンダーで管理する |
| **メニュー表** | 「この中から選んでね」と**お店のように見せる料理の並び**。テーマ（レストラン・和食屋など）を選んで表示する。献立とは別のもの |
| **テーマ** | メニュー表の見た目（レストラン・和食屋・料亭・居酒屋・ファミレス風など） |
| **ジャンル** | レシピの分類（和風・洋風・おつまみ・デザート・一品料理など）。ユーザーが自由に作れる。**1つのレシピに複数付けられる** |
| **「作った」記録** | 実際に作った日付の記録。点数・メモは任意 |
| **定番の版** | レシピの中で「いつもはこれ」と選んだ版。一覧やメニュー表ではこの版を表示する。選んでいなければ最新の版を表示する |

> 版と派生レシピの線引きはユーザーが選ぶ（アプリは迷ったときの目安を示す）。

## 1. 機能要件（できること）

### 1-1. レシピの登録・管理

- レシピを登録・編集・削除できる
- 入力のハードルを下げるため、**必須は料理名だけ**。ほかはすべて任意で、あとから少しずつ書き足せる
  - 任意項目：完成写真、元の情報（動画・サイトのURL）、何人分か、材料（名前・分量・単位）、手順、調理時間、難易度、ひとことメモ
- 完成写真は**1〜2枚**。手順ごとの写真も追加できる（任意）

### 1-2. 版（アレンジ版）

- レシピを登録すると、その内容が**元の版**になる
- 既存の版をもとに**アレンジ版**を作れる。もとの版の内容（材料・分量・手順・写真）を**そのまま引き継ぎ**、変えたいところだけ編集・写真を入れ替えできる
- アレンジ版は自由に削除できる。元の版は削除できない
- 版の1つを**定番の版**に選べる。一覧やメニュー表では定番の版を表示し、選んでいなければ最新の版を表示する

### 1-3. 派生レシピ

- 既存のレシピをもとに、別の料理として**派生レシピ**を作れる（例：鶏の照り焼き → 豚の照り焼き）
- 派生レシピは独立したレシピで、**派生元のレシピ**へのつながりを持ち、互いにたどれる

### 1-4. 分量の基準と自動換算

- 版ごとに、分量が**何を基準に書かれているか**（**分量の基準**）を選んで登録する。元のレシピの書き方に合わせられるようにするため
  - **人数**：例）2人分
  - **個数**：例）クッキー20枚分、ハンバーグ4個分
  - **型のサイズ**：例）18cmの丸型
  - **材料**：例）鶏もも肉300gあたり
- 表示中の版の分量を、次のいずれかの基準で換算して表示できる（元のデータは書き換えない）
  - **人数**：例）2人分 → 3人分
  - **型のサイズ**：例）18cmの丸型 → 15cmの丸型。型の**面積の比**で換算する（(15÷18)² ≒ 0.69倍）
  - **材料1つを基準**：例）鶏肉300g → 450gに合わせて、全体を1.5倍にする
- 「少々」「適量」など数値でない分量は換算せず、そのまま表示する

### 1-5. 評価と「作った」記録

- レシピに**点数（★5段階）とレビューを1つ**持てる。いつでも上書きでき、書かなくてもよい
- 「作った」ボタンで**作った日付**を記録できる。点数・メモは任意（書かなくてもよい）
- 「作った」記録には、**どの版を作ったか**が自動で残る。履歴から版ごとの出来を比べられる
- 記録から「最後に作った日」「作った回数」が分かる

### 1-6. 研究メモ

メモは2種類あり、役割を分ける。

| | 版のメモ | 「作った」記録のメモ |
| --- | --- | --- |
| 書くこと | その版の説明・コツ（例：砂糖を控えた版、火加減は弱火が正解） | その回の振り返り（例：塩が多かった。次は控える） |
| 性質 | 上書きして育てる（結論） | 日付ごとにたまる（試作の記録） |

- 「作った」記録から、**その気づきをもとにアレンジ版を作れる**（作る → 振り返る → アレンジ版を作る → また作る、という研究のループ）

### 1-7. メニュー表

- メニュー表を自由に作成・編集・削除できる（例：今週の晩ご飯メニュー、週末の居酒屋メニュー）
- メニュー表には**店名**を付けられる（例：和食屋 ○○）。日付・期間は持たない
- メニュー表に**テーマ**（レストラン・和食屋・料亭・居酒屋・ファミレス風など）を選び、そのテーマで表示できる
- レシピを選んでメニュー表に登録する。表示されるのは各レシピの定番の版
- メニュー表の中を**区切り（セクション）**で分けられる。区切りの名前は自由（例：前菜・メイン・デザート、おつまみ・焼き物・〆）
- 料理の並び順を変えられる
- 料理ごとに、レシピとは別の**メニュー用の説明文**（例：じっくり煮込んだ自慢の一品）を付けられる
- 料理の写真の出し方は**テーマごとに決める**（例：ファミレス風は写真を大きく、料亭は文字だけで品よく）
- 価格は第1段階では持たない（要望があれば検討。企業モードでは必要になる）

### 1-8. 献立

- 日付に料理（レシピ）を並べて、「いつ何を作るか」を予定できる
- 朝・昼・夜などの区切りは第1段階では持たない（未決事項を参照）

## 2. 非機能要件（どう動いてほしいか）

第1段階は自分用の試作という位置づけ。作り込みすぎず、将来の公開版へ育てられる土台にすることを優先する。

- **動作環境**：`docker-compose`でローカル完結。ログイン（認証）なし
- **画面**：スマホとPCの両方で使える（レスポンシブ）。キッチンで見るスマホ画面を優先して設計する（モバイルファースト）
- **キッチンでの操作性**：大きめの文字とボタン、高いコントラスト、少ない操作で「見る・確認する」ができること
- **入力のしやすさ**：必須項目は最小限。材料・手順は行をすばやく追加・並べ替えできること
- **写真**：アップロード時に表示用のサイズへ縮小・圧縮し、一覧の表示を重くしない
- **言語**：日本語のみ
- **データの保全**：データと写真をまとめて書き出し・復元できる**開発用コマンド**（`make backup` / `make restore`）を用意する。アプリ画面からの書き出し機能は公開版（第3段階）で検討する

## 3. スコープ（第1段階でやること・やらないこと）

### やること（第1段階）

- レシピの登録・管理（1-1）、版（1-2）、派生レシピ（1-3）
- 分量の基準と自動換算（1-4）
- 評価と「作った」記録（1-5）、研究メモ（1-6）
- メニュー表（1-7）とテーマ（まずは**レストラン**と**和食屋**の2種類）
- 献立（1-8）
- バックアップ・復元コマンド

### やらないこと（将来段階で検討）

- ログイン・公開・ユーザー間の共有
- AIによるレシピの自動取り込み
- メニュー表の価格、企業モード（組織・店舗）
- 買い物リスト（材料の逆算）
- 画像・PDFの書き出し、SNS共有
- ジャンル（設計が必要なため、第1段階の後半〜次段階）
- ブログ・日記の公開、収益化、栄養・カロリー計算、注文・決済

## 4. 優先度（実装の順番の目安）

この順にIssueを切る。

- **必須**：レシピの登録・管理（1-1）、版（1-2）
- **重要**：分量の基準と自動換算（1-4）、メニュー表とテーマ（1-7）、評価と「作った」記録（1-5）、研究メモ（1-6）、バックアップ・復元コマンド
- **あると便利**：派生レシピ（1-3）、献立（1-8）、ジャンル

## 5. 未決事項（設計で詰める課題）

- **献立とメニュー表の関係**：メニュー表は「ここから選んでね」という選択肢、献立は「いつ何を作るか」の予定。メニュー表から選んだ料理を献立に入れる流れや、献立からメニュー表を作る流れが必要か、両者をどうつなぐかは設計で詰める
- **献立の区切り**：朝・昼・夜（や弁当・おやつ）で分けるかは、献立の使い方が見えてから設計する
- **写真の引き継ぎ方**：アレンジ版は写真を引き継ぎ、一部だけ入れ替えられる。写真を版ごとにコピーせず、中間テーブルで版と写真を紐付ける方式を想定（`03_data_model.md`で詰める）
- **ジャンルの設計**：複数付けられることは決定。階層（例：和風 > 煮物）を持つか、タグとの違いをどうするか、初期値を用意するかは未定
