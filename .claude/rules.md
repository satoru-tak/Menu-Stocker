# Menu Stocker 開発ルール

## 基本方針

### 言語設定
- **すべての回答は日本語で行う**
- コードコメントも日本語で記述
- 変数名、関数名は英語（規約に従う）
- コミットメッセージは日本語

### コーディング規約

#### Ruby/Rails
- Rubocop の規約に従う
- メソッド名は snake_case
- クラス名は PascalCase
- 定数は SCREAMING_SNAKE_CASE
- RESTful な API 設計
- バージョニング: `/api/v1/`

#### TypeScript/React/Next.js
- ESLint + Prettier の規約に従う
- コンポーネント名は PascalCase
- ファイル名はコンポーネントに合わせる
- hooks は use から始める
- 型定義を必ず行う
- Server Components を優先的に使用

### ディレクトリ構造

#### Backend (Rails)
```
backend/
├── app/
│   ├── controllers/
│   │   └── api/
│   │       └── v1/
│   ├── models/
│   ├── serializers/
│   └── services/
├── config/
├── db/
│   ├── migrate/
│   └── seeds/
└── spec/
```

#### Frontend (Next.js)
```
frontend/
├── src/
│   ├── app/              # App Router
│   ├── components/       # 共通コンポーネント
│   ├── features/         # 機能ごとのコンポーネント
│   ├── lib/              # ユーティリティ
│   ├── types/            # 型定義
│   └── styles/           # グローバルスタイル
├── public/
└── tests/
```

### Git コミット規約

Conventional Commits（日本語版）を使用：

```
feat: 新機能
fix: バグ修正
docs: ドキュメントのみの変更
style: コードの意味に影響を与えない変更（空白、フォーマットなど）
refactor: バグ修正や機能追加ではないコード変更
perf: パフォーマンス改善
test: テストの追加や修正
chore: ビルドプロセスやツールの変更
```

例：
```
feat: レシピ作成機能を追加
fix: メニュー表示時の画像読み込みエラーを修正
docs: API仕様書にメニューエンドポイントを追加
```

### テスト方針

#### Backend
- モデルのバリデーションテスト必須
- コントローラーのAPIテスト必須
- カバレッジ 80% 以上を目標

#### Frontend
- コンポーネントの単体テスト
- 重要な機能の統合テスト
- カバレッジ 70% 以上を目標

### ドキュメント

- 新機能追加時は必ず docs/ 配下に設計書を追加
- API変更時は api/ 配下のドキュメントを更新
- データベース変更時は database/ 配下のドキュメントを更新

### セキュリティ

- 環境変数は .env に記載し、.gitignore に追加
- API キーやパスワードはコードにハードコーディングしない
- ユーザー入力は必ずバリデーション
- SQL インジェクション対策（Rails の ActiveRecord を使用）
- XSS 対策（React のデフォルト動作を利用）

### パフォーマンス

- N+1 クエリを避ける（includes, preload を使用）
- 画像は最適化してアップロード
- API レスポンスにページネーションを実装
- 適切なインデックスをデータベースに設定

## 開発フロー

1. **Issue 作成**: 機能や修正内容を明確に記述
2. **ブランチ作成**: `feature/機能名` または `fix/修正内容`
3. **実装**: ルールに従ってコード作成
4. **テスト**: 必要なテストを作成・実行
5. **コミット**: Conventional Commits に従う
6. **Pull Request**: テンプレートに従って作成
7. **レビュー**: コードレビューを受ける
8. **マージ**: main ブランチにマージ

## Claude Code の使い方

### 質問の仕方
- 具体的に何を実装したいか明確に伝える
- 「〇〇機能を実装したい」「〇〇のエラーを修正したい」
- 関連するファイルパスを提供する

### コード生成
- 一度に大きな機能を実装せず、小さな単位で進める
- 生成されたコードは必ずレビューする
- テストコードも同時に生成を依頼する

### ドキュメント作成
- 設計書、API仕様書、ER図などの作成を依頼可能
- Markdown 形式で docs/ 配下に保存

## 注意事項

- **段階的な実装**: 一度に全機能を実装せず、MVP から始める
- **テスト駆動**: 可能な限りテストを先に書く
- **レビュー**: 自動生成コードも必ず内容を確認
- **ドキュメント更新**: コード変更時は関連ドキュメントも更新
